# 排车服务

面向城配调度系统的排车（多车型装箱）服务。每天截单后，调度系统把一批货和一组车型
通过 HTTP 提交上来，服务以**作业**方式异步求解：持续改进方案，随时可查当前最好
方案、下界与相对差距，可取消，到时间上限自动停止并交出当时最好的完整可行方案。

## 问题定义

- **货**：编号、重量、体积、所属互斥类别（可空）、是否必须独占一车。
- **车型**：载重上限、容积上限、单车包车费、可用数量上限。
- **冲突**：调用方给出互相冲突的类别对，冲突类别的货不能同车。
- **目标**：每票货恰好上一辆车；每车不超载不超容；冲突货不同车；独占货独占；
  车型用量不超上限；总包车费尽量低。

服务不保证最优，但每个作业都给出**下界**并报告当前方案与下界的**相对差距**。

## 快速开始

```bash
# Docker（数据文件挂在卷上）
docker build -t fleet-scheduling .
docker run -p 8000:8000 -v fleet-data:/data fleet-scheduling

# 本地开发
pip install -r requirements-dev.txt
uvicorn app.main:app --port 8000
pytest                 # 跑单元测试
```

数据文件路径由环境变量 `APP_DB_PATH` 指定，默认 `/data/app.db`。

## API

### 提交作业 `POST /jobs`

```json
{
  "problem": {
    "items": [
      {"id": "A1", "weight": 6, "volume": 2, "category": "food"},
      {"id": "B1", "weight": 5, "volume": 3, "category": "chemical"},
      {"id": "V1", "weight": 2, "volume": 1, "exclusive": true}
    ],
    "vehicle_types": [
      {"name": "van",   "max_weight": 10, "max_volume": 12, "cost": 100, "count": 5},
      {"name": "truck", "max_weight": 25, "max_volume": 40, "cost": 180, "count": 2}
    ],
    "categories": ["food", "chemical"],
    "conflicts": [["food", "chemical"]]
  },
  "options": {"seed": 7, "time_limit_seconds": 30}
}
```

- `items[].volume` 缺省 0；`category` 缺省 null（不参与互斥）；`exclusive` 缺省 false。
- `categories` 可空；类别全集取"声明的类别 ∪ 货物用到的类别"。
- `options.seed` 缺省 0；`options.time_limit_seconds` 缺省 30，上限 3600。
- 成功返回 `201` 与作业对象（含作业号与下界）；输入非法返回 `422`，
  `detail` 是错误列表，每条都指出具体字段，例如：

```json
{"detail": [{"field": "items[3].weight", "message": "must be a finite number >= 0"}]}
```

会被指出的输入错误包括：重量/体积为负或不是有限数（`items[i].weight` 等）、
某票货比任何车型都大（`items[i]`）、独占货多于所有车型可用总数（`items`）、
冲突关系引用不存在的类别（`conflicts[i]`）、车型字段非法
（`vehicle_types[i].max_weight` 等）、货物编号重复（`items[i].id`）、
总载重/总容积明显不够（`vehicle_types`）。

### 查询 `GET /jobs/{job_id}`

```json
{
  "job_id": "…",
  "status": "running",                 // running|completed|cancelled|interrupted|failed
  "stop_reason": null,                 // optimal|exhausted|time_limit|cancelled|interrupted
  "lower_bound": {"cost": 158.4, "vehicles": 1, "tightest": "weight", "details": {…}},
  "best_solution": {                   // 当前最好方案，运行中持续刷新；null 表示还没有
    "vehicle_count": 3,
    "total_cost": 380.0,
    "vehicles": [
      {"vehicle_type": "van", "items": ["V1"], "load_weight": 2.0, "load_volume": 1.0}
    ]
  },
  "best_cost": 380.0,
  "gap": 1.399,                        // (best_cost - 下界) / 下界
  "proven_optimal": false              // 费用达到下界即为 true
}
```

- `GET /jobs` 列出全部作业；`POST /jobs/{job_id}/cancel` 取消（幂等，
  返回最终状态）。已结束的作业再取消直接返回现状。
- `stop_reason`：`optimal`=已证明最优（费用=下界）；`exhausted`=搜索预算用完；
  `time_limit`=到时间上限；`cancelled`=被取消；`interrupted`=服务重启中断。
- 不管取消还是超时，交出的 `best_solution` 都是**完整可行**的：
  求解器每个改进动作都是先算好再整体生效，停止只发生在动作之间；
  方案落库前还会经过一次独立校验，校验不过宁可不交。

### 持久化与重启

作业与方案全部落 SQLite（WAL 模式）。服务重启后：已完成的作业和方案原样保留；
重启前没跑完的作业在启动时被标为 `interrupted`，其中断前已改进出的方案仍可查询。

## 下界怎么推

从三个角度分别推导，再取最紧的一个（`lower_bound.tightest` 标明哪个起了作用，
`details` 里有各角度的中间值）：

1. **重量**：车辆数 ≥ ⌈总重 / 最大载重⌉；费用 ≥ 总重 × min(单车费/载重)。
2. **体积**：同理，把载重换成容积。
3. **独占**：车辆数 ≥ 独占票数；费用 ≥ 每票独占货"能装下它的最便宜车型"之和。
4. （派生）费用 ≥ 车辆数下界 × 最低单车费。

重量/体积费用界是连续松弛（允许按吨/按方"切开"买运力），因此恒为有效下界。
全部用分数精确计算，保证：**多加一票货下界不降**；**全部重量和载重乘同一个正数，
车辆数下界不变**。例：4 票货 6/5/5/4 吨、只有 10 吨车型、容积不起作用时，
重量角度给出 2 辆、费用界 = 2 倍单车费，`tightest = "weight"`。

注意：下界是单维松弛，货物同时受两种维度约束、或受互斥/独占约束时，下界会偏松，
此时报告的 gap 是"真实最优差距"的上界，并不代表方案差。

## 求解方法：构造式启发 + 局部搜索 + 迭代局部搜索

**为什么选它**（而不是列生成 / 分支定界）：

- **Anytime**：从构造完成的第一刻起就持有完整可行解，之后单调改进——正好匹配
  "提交即返作业号、随时查最好方案、到点交卷"的作业模型。分支定界在证明最优前
  常常长时间没有可行解或只有很差的解。
- **确定性**：所有随机选择都来自 seed 初始化的随机源，搜索轮数预算只随票数变化，
  同输入同种子轨迹完全一致（时间上限截断除外，见下）。列生成涉及 LP 求解器，
  数值容差与机器环境会渗入结果，难以保证逐位一致。
- **约束处理直接**：互斥、独占、车型数量上限在邻域动作里都是廉价的局部检查；
  列生成/分支定界要把这些塞进定价子问题，建模与实现成本高得多。
- 几百票的规模下，经验上这类启发式的解质量足够，且 1 小时内的时间预算绰绰有余。

**流程**：

1. **构造**：独占货先各自开"能装下它的最便宜且还有数量的车型"（可装车型少的优先）；
   其余货按重量降序 best-fit 装入现有车（装后剩余载重最小者），装不下开新车。
2. **局部搜索**（只接受严格降费的动作，因此必终止）：
   - *换型*：在数量限制内给每辆车重新指派最便宜车型；
   - *整车消除*：把某辆车的货全部并入其它车，省掉一整车的包车费；
   - *迁移*：把一票货移到另一辆车，源车与目标车同时最优换型后费用下降则接受
     （能完成"两辆小车并一辆大车"这类合并）。
3. **迭代局部搜索**：对当前解随机搬动几票货做扰动，再跑局部搜索；更好则接受，
   连续无改进则回到历史最好解重新扰动。轮数预算 = max(40, min(400, 30+n))，
   费用降到下界时提前停止并标记 `optimal`。

**容易陷在较差解的情形**（如实说明）：

- **需要整体搬空一辆装得较满的车才更优**的实例：迁移动作一次只搬一票，
  整车消除只尝试票数较少（≤12）的车，超过这个规模的"联合搬迁"看不到；
- **车型多且价格接近、货物尺寸集中在半载附近**：经典装箱难例，best-fit 构造
  留下的碎片多，局部搜索的改进空间被切碎；
- **互斥关系稠密**：可行邻域稀疏，扰动后大量重新插入失败，等于搜索步长变小；
- **时间上限给得太低**：ILS 还没走出构造解的邻域就被截断。
  此外下界本身偏松时，即使方案已是最优也无法被证明（`proven_optimal=false`）。

**运行时间随票数的增长**：单次局部搜索约 O(n·V)（n 票货、V 辆车，V 大致随 n
线性增长），ILS 轮数预算随 n 线性（370 票后封顶 400 轮）。因此小票段接近 O(n³)、
大票段约 O(n²)。实测（本仓库开发机，随机数据）：100 票 0.03s、300 票 0.4s、
500 票 1.0s、1000 票 2.8s、2000 票 12.6s、3000 票 35s。生产上由时间上限截断，
实际等待不会超过 `time_limit_seconds`（加少量收尾开销）。

## 确定性与精确性设计

- 重量/体积在载入时按小数位数放大为整数（JSON 数都是有限小数，缩放精确），
  求解全程整数运算：容量判断无浮点误差，且**全部重量和载重乘同一个正数时，
  所有比较结果不变，车辆数不变**。
- 随机数只来自 `random.Random(seed)`；搜索预算只随票数变化。
  **同输入同种子，结果完全相同**——前提是搜索在时间上限内跑完预算轮数；
  若被时间上限截断，截断点依赖机器时序，这是任何限时搜索的固有性质。
  需要逐位复现时，给足时间上限即可。

## 代码结构

```
app/
  main.py          # FastAPI 路由与作业装配
  schemas.py       # 请求模型
  validation.py    # 业务校验（指出具体字段）
  store.py         # SQLite 持久化
  jobs.py          # 作业管理（后台线程、取消、关停语义）
  solver/
    types.py       # 内部表示与整数缩放
    bounds.py      # 下界
    solver.py      # 构造 + 局部搜索 + ILS
    check.py       # 方案可行性独立校验
tests/             # pytest：下界性质、求解器性质、API 行为、输入校验
```
