# 排车算法说明

## 1. 问题定位

输入一批货（重量、体积、互斥类别、是否独占）和若干车型（载重、容积、包车费、可用数量），
求一组车与装载方案，使：

- 每票货恰好上一辆车；
- 每辆车不超载、不超容；
- 冲突类别的货不同车（含"同类自冲突"）；
- 独占货独占一车；
- 各车型用量不超过可用数量；
- 总包车费用最小。

这是带**异构车型固定费用**的二维装箱问题（2D bin packing / fixed-charge）
叠加图着色式的类别互斥与独占约束，属 NP-hard。"用哪种车"与"怎么装"两个决策耦合，
精确算法在几百票规模无法在一小时窗口内保证求到最优，因此本服务定位为
**anytime 启发式 + 可证明的费用下界**，报告相对差距而不冒充最优。

## 2. 为什么选"构造式启发 + 局部搜索 + ILS"，而不是列生成 / 分支定界

候选方案比较：

| 方法 | 优点 | 不采用/不主用的原因 |
| --- | --- | --- |
| 分支定界（精确） | 能给最优与严格界 | 二维装箱 + 异构固定费用的分支树在几百票时极易爆炸，1 小时无法收敛，且 anytime 特性差（中途只有不可直接交付的界） |
| 列生成 | 适合"路线/装载模式很多、线性松弛紧"的场景 | 主问题要处理独占与互斥的整数性，列（可行装载组合）本身就是一个装箱难题；工程复杂、首解慢、确定性难保证 |
| **多策略构造 + 局部搜索 + ILS** | 首解毫秒级、随时可交付完整可行解、易加领域知识、随机种子可完全确定 | 不保证最优，依赖下界报告质量——正是需求允许的取舍 |

服务在两个子结构上仍然使用**精确优化**，不浪费可证明的部分：

1. **独占货 → 车型的指派**用最小费用流（二分匹配），在"每票独占一车"前提下费用最优，
   同时直接给出独占下界。
2. **给定货物分组后，各车 → 车型的选择**用"逐车最便宜可行车型 + 可用量约束"贪心，
   触碰可用上限时回退最小费用流，求当前分组下可证明最优的车型指派。

把"货物怎么分组"（难、启发式）与"每组用什么车"（可精确、多项式）解耦，是本实现的主线。

## 3. 算法流程

1. **下界计算**（每次作业先算，毫秒级），见第 4 节。
2. **独占货落位**：用最小费用流把独占货指报到费用最小的可行车型，各开一辆车。
3. **多策略构造**：非独占货分别按 重量降序 / 体积降序 / 密度（重/泡）降序 /
   相对最小可行车型的归一占用降序，配合最佳适配，构造 4~6 个确定性初始解，取最省者。
4. **局部搜索**（确定步数）：
   - 车型再优化（贪心/最小费用流）；
   - 整车合并：两辆车类别相容、合并后能整体塞进某车型且费用不升高则合并，
     合并允许升级到大车型；**等费用但少一辆车的平台移动也接受**，为后续三车并一车铺路；
   - 交换助攻：一次对换化解一票货的类别阻碍后再合并；
   - 搬迁：把一票货搬到别的车以清空源车（少一辆车）或降费。
   邻域评估全部在可行解之间进行，用 O(K) 的"合并后最便宜车型"做预筛，
   只有可能改进时才做全局指派，保证大规模也能跑动。
5. **迭代局部搜索（ILS）**：对当前最好解随机扰动（随机把若干票货搬走，允许开新车），
   再局部搜索，更省则替换全局最好解。扰动强度与随机数全部来自种子。

**Anytime 完整性**：内部从不维护"改到一半"的方案——每个被接受的移动本身可行，
ILS 只在独立校验通过后才替换最好解。因此取消或停止时交出的一定是完整可行方案；
落盘前与读回后还各有一次独立校验（`app/verify.py`）兜底。

## 4. 下界（取最紧者，并报告是哪一维起作用）

下界在放松"货物不可分割/部分整数约束"的同时**不放松任何真实约束**，
因此必然 ≤ 任一可行方案费用。计算五个维度，取费用最大者：

1. **平凡下界**：有货至少一辆车，费用不低于最便宜车型。
2. **重量**：总重量按"单位载重费用最便宜"的车型做分数装载（允许切开货）；
   再与考虑各车型可用辆数的分数装载 LP 取较紧者，后者容量不足即直接判定不可行。
3. **体积**：同理。
4. **独占货**：最小费用流匹配费用（每票独占一车、车型可用量受限）。
5. **互斥**：
   - 普通冲突对 (A,B)：A、B 的车不共享，各自按重量、体积两维做分数装箱下界后相加；
   - 自冲突 (A,A)：同类两两不能同车，每票必须独占一辆可行车型，费用逐票相加。

最终费用下界 = max，`binding` 字段报告起决定作用的维度，各维的明细也一并返回。

**分数下界与整数方案之间存在固有间隙**（如 4 吨货、5 吨车：分数 1.6 辆 vs 整票 2 辆），
这是装箱问题的本质，差距报告会如实体现；当方案费用触达下界即标记"已证明最优"。

## 5. 容易陷在较差解的数据

启发式不保证最优，以下几类数据上差距可能偏大，调度员应结合差距报告判断：

- **重量与体积两个维度交替吃紧**（一批重货、一批泡货混排）：单一排序策略只能照顾一维，
  需要靠 ILS 多次重启弥补；时限短时可能停在 10%~30% 差距。
- **车型费用接近、容量档位密集**：大量等费用平台移动，局部搜索容易在平台上打转，
  改进取决于扰动是否跳出。
- **互斥类别多且每类票数大**：可行车对被大量剪枝，整车合并/搬迁命中率下降，
  着色式约束会抬高真实车辆数（分数下界此时偏松，差距看起来偏大但不代表方案差）。
- **车型可用上限很紧**：贪心指派频繁触碰上限、回退最小费用流，且很多本可合并的分组
  因配额被占而放弃，解质量对配额分布敏感。
- **独占货占比高**：可优化空间被锁死，费用主要由独占匹配决定（该部分其实已最优）。
- **几百票且时限很短（如 <1 秒）**：初始解占比大、ILS 轮数少。

构造阶段若全部确定性策略都失败，会用带随机的 GRASP 兜底以保证尽量找到可行解。

## 6. 运行时间随票数的增长

- 下界、最小费用流指派：约 O(E·K) 到 O(V·K·log)，几百票内毫秒~十毫秒级。
- 单次构造：O(n²·K) 最坏（最佳适配扫描车列）。
- 一轮局部搜索：合并是 O(V²·K) 的平方邻域，搬迁扫描近似 O(n·V·K)；
  实测单轮在 n≈100 时约数毫秒，n≈600 时约 0.1~0.2 秒（笔记本/容器量级）。
- 总耗时主要由**时间上限**决定（anytime）：服务按 `time_limit_seconds` 运行，
  在时限内尽量多跑 ILS 轮。票数越大，同样时限内轮数越少（平方增长），
  因此大实例更依赖构造与首轮局部搜索的质量。

## 7. 确定性（同输入同种子）与"跑到时间上限"的取舍

这两个要求在共享/负载波动的机器上存在张力：若按墙钟在任意位置停，
"停在第几轮"会随机器负载抖动，结果就不可逐位复现。本服务的处理：

- **每个 ILS 轮的结果只由随机种子与固定步数预算决定，完全不看墙钟**；
- 要跑多少轮，由 `(time_limit_seconds, 票数, 车型数)` 与一个**进程内一次性标定的
  机器速度常数**确定性地算出；标定常数在服务进程生命周期内固定。
- 因此同进程内同输入同种子严格逐位一致（HTTP 调用场景即如此）；
  实际墙钟会尽量贴近但**允许略短或略长于**设定值——优先保证可复现与可行。
  跨不同机器，墙钟不同，但结果仍是种子的确定函数。
- 取消不依赖时间：取消信号在轮/趟边界检查，何时取消由调用方决定；
  在相同取消节奏下结果同样确定。

若业务更看重"严格不超过 N 秒"而非跨负载的逐位一致，可把第 7 步的轮数公式
改为墙钟门控（代码中留有明确位置），但同种子结果会随机器负载有小差异。

## 8. 停止状态

- `completed`：方案费用已触达下界，**已证明最优**（在该下界意义下）；
- `timeout`：到达时间预算仍未触达下界，交出当时最好的完整可行方案；
- `cancelled`：被取消，交出当时最好的完整可行方案；
- `interrupted`：服务重启时仍在跑的作业，标记为中断（其最后落盘方案仍可查）；
- `infeasible`：下界阶段已证明无可行方案（如总容量不足、独占货无车型可配）。

## 9. 主要模块

- `app/models.py`：领域模型与方案的增删（唯一状态修改入口，维护重量/体积/类别计数）。
- `app/mincostflow.py`：势函数 Dijkstra 的最小费用流。
- `app/bounds.py`：五维下界与独占匹配。
- `app/solver.py`：构造、局部搜索、ILS、确定性标定。
- `app/verify.py`：独立可行性校验（与求解逻辑分开实现）。
- `app/jobs.py`：作业线程、节流落盘、取消、重启恢复。
- `app/db.py`：SQLite（WAL）持久化。
